## 1. 핵심 제품 원칙 (2-1 인터뷰에서 도출)

> ### 사무 노동은 제거하고, 묵상 노동은 보호한다.
>
> - 365qt 본문·질문 타이핑 = **사무 노동** (옮겨 적기) → 자동화로 제거
> - 찬양 가사 타이핑 = **묵상 행위 그 자체** ("직접 타이핑하며 가사를 묵상하고 돌아본다") → 자동화 금지
> - 이후 모든 자동화 기능 제안 시 반드시 묻는다: **"이건 옮겨 적기인가, 묵상인가?"**
> - 부수 효과: 가사 자동 수집을 하지 않으므로 가사 크롤링 저작권 리스크 자연 회피

## 2. 루틴별 JTBD (Phase 2-1)

### 2.0 공통 사실

- **작성의 95% 이상이 데스크탑.** 데스크탑 작성 경험이 1순위
- 모바일은 "크롤링 덕분에 가능해지는 보너스" 포지션. 단 QT 답변 작성만큼은 모바일에서도 스트레스 없어야 함 (크롤링 가치의 완성 조건)
- 임시저장을 실제로 사용 중 → **자동 저장 + 이어쓰기 복귀는 확정 요구사항**

### 2.1 QT 묵상 (말씀 묵상)

| 항목 | 내용 |
|------|------|
| 상황 | 평일: 회사 점심시간. 주말: 유동적 (찬양과 연달아) |
| 트리거 | 요일 (월~토) |
| 기기 | 데스크탑 95% → 크롤링 후엔 장소·기기 불문 가능 |
| 현재 소요 | 약 20분, 그중 상당분이 365qt를 보며 본문·질문을 옮겨 적는 타이핑 |
| 기대 결과 | 에디터를 열면 **본문·질문이 채워진 오늘의 초안이 이미 대기**. 답변 6개 + Summary만 작성. 입력 노동 0분 |
| 설계 요구 | 1탭 진입, 자동 저장, 이어쓰기 복귀, 크롤러 실패 시에도 빈 QT 템플릿 1탭 생성 (수동 폴백) |

### 2.2 설교 묵상 — ⚠️ 별도 요구사항 등급

| 항목 | 내용 |
|------|------|
| 상황 | **일요일 예배당, 설교를 들으며 실시간 타이핑** |
| 트리거 | 설교 시작 |
| 기기 | 노트북 |
| 현재 방식 | 티스토리 에디터에 직접 실시간 작성 → 발행. **다듬는 작업 없음** (전송·정리 단계 자체가 없음) |
| 기대 결과 | 라이브 노트테이킹: 즉시 시작, 설교 속도를 따라가는 빠른 입력, 끝나면 바로 발행 |
| 설계 요구 | **절대 유실 금지** — 예배당 네트워크가 불안해도 로컬 우선 저장으로 살아있을 것. 복구 UI. 방해 요소(팝업, 자동 포커스 이동 등) 제로 |

다른 묵상과 성격이 다름: QT는 차분히 앉아 쓰는 글, 설교는 라이브 속기. 에디터 설계를 분리해서 사고할 것.

### 2.3 찬양 묵상

| 항목 | 내용 |
|------|------|
| 상황 | 평일 퇴근 후 집, 하루 마무리 (기도문으로 마침) |
| 트리거 | 매일 밤 |
| 기기 | 데스크탑 |
| 기대 결과 | YouTube URL 1회 붙여넣기 → 임베드 + `아티스트 - 곡명` 제목 자동 제안. **가사는 직접 타이핑** (묵상 행위 — 자동화 금지) |
| 설계 요구 | 섹션 블록(Intro/Verse/Pre-Chorus/Chorus/Bridge/Interlude/Outro) 추가·정렬이 타이핑 흐름을 끊지 않는 UX. 하단 기도문 영역 |

### 2.4 기술 글

| 항목 | 내용 |
|------|------|
| 상황 | 비정기. 쓰고 싶은 주제가 생겼을 때 |
| 트리거 | 주제 발생 + AI 협업으로 작성 |
| 기기 | 데스크탑 |
| 기대 결과 | Notion식 WYSIWYG 작성 |
| 설계 요구 | **마크다운 붙여넣기 → 서식 자동 변환** (AI 산출물은 마크다운으로 오므로, AI 협업 워크플로우의 핵심 진입점) |

## 3. 사이트 구조 (Phase 2-2)

### 3.1 결정: 서브도메인 분리 + 프로필 허브

독자 두 집단(검색 유입 개발자 vs 신앙 콘텐츠 독자)의 공존 문제에 대해 **(c) 서브도메인 분리**를 선택. 루트 도메인은 **(a) 프로필 허브**로 확정.

```
○○○.com          → 프로필 허브 (광일 소개, 두 블로그 입구, GitHub/LinkedIn)
dev.○○○.com      → 기술 블로그
faith.○○○.com    → 묵상 블로그
(서브도메인 명칭은 예시. 브랜드명과 함께 Phase 4에서 확정)
```

### 3.2 구조 결정의 근거와 파급

| 영역 | 내용 |
|------|------|
| 아키텍처 | **하나의 Next.js 앱 + middleware 호스트 분기.** DB 하나(posts.type으로 필터), 관리 화면 하나, 크롤러 하나. "세 개의 얼굴, 하나의 몸" — 유지보수 부담이 3배가 되지 않음 |
| SEO | 검색엔진은 서브도메인을 사실상 별도 사이트로 취급 → 기술/묵상 각각 주제 일관성 확보 (유리). 서치콘솔·sitemap은 사이트별로 각각 등록 |
| 통계 | 사이트별 분리 집계가 자연스러움 (티스토리 시절 두 블로그 분리 운영 경험과 일치) |
| 디자인 | 디자인 시스템 1벌 공유 + 사이트별 무드 변수 오버라이드 (Phase 4에서 구조 설계) |
| 정체성 | 허브 = "이력서에 쓸 수 있는 내 주소". 개발자 정체성 동기와 정합 |

### 3.3 허브 v1 범위 (프리모템 #11 예방)

**정적 한 페이지로 극소화**: 이름, 한 줄 소개, 두 블로그 카드, GitHub/LinkedIn 링크. 끝.
경력·프로젝트 상세·이력서 페이지는 Backlog. 갱신할 게 없을 만큼 단순하면 낡지도 않는다.

### 3.4 도메인 상태

- **미구매.** Vercel 기본 주소로 개발·테스트 진행, 구매는 공개 직전
- 도메인 이름은 브랜드명 결정(Phase 4)과 함께 선정. 도메인 1개 구매로 서브도메인은 무한 생성 (추가 비용 없음)
- 예상 고정비: 연 2만원 안팎 — 이 프로젝트의 유일한 고정비 (나머지는 무료 티어)

## 4. 프리모템 (Phase 2-3)

> 가정: "2027년 2월, 이주 6개월 뒤 새 블로그가 방치되고 티스토리로 돌아갔다." 왜?

| # | 사망 원인 | 예방 장치 | 치명도 |
|---|----------|----------|--------|
| 1 | 크롤러가 죽었는데 고치기 귀찮아서 QT 루틴이 티스토리로 회귀 | Slack 즉시 알림 + 수동 폴백(빈 QT 템플릿 1탭 생성). 크롤러 없이도 티스토리보다 나은 상태 유지 | **최상** |
| 2 | 예배 중 설교 글 유실 사고 1회 → 도구 신뢰 상실 | 로컬 우선 저장(네트워크 무관) + 복구 UI. 한 번의 유실이 전체 신뢰를 죽인다 | **최상** |
| 3 | UI가 계속 거슬리는데 못 고쳐서 정 떨어짐 | Phase 3~4 디자인 투자 + 출시 후 "거슬림 목록" 이슈 즉시 기록 습관 | 중 |
| 4 | 검색 유입 0 지속 → 통계 볼 맛 상실 → 동기 붕괴 | 기대치를 문서에 명시(6개월 50%) + 유입 외 지표(작성 스트릭, 누적 글 수) 병행 표시 | 중 |
| 5 | 마이그레이션 방치로 글이 두 곳에 분산 | 마이그레이션 포함 여부를 Phase 8에서 명시 결정 | 중 |
| 6 | 의존성 부패로 빌드 깨짐 → 방치 | 의존성 최소화 + 락파일 고정. "안 만지면 안 깨지는" 구조 | 중 |
| 7 | 무료 티어 초과/일시정지 | 트래픽은 한도의 1% 미만. Supabase 7일 비활성 정지는 크롤러의 매일 쓰기가 자연 방어 | 하 |
| 8 | 모바일 답답 → "나중에 컴퓨터로" → 그 나중이 안 옴 | QT 답변 작성만큼은 모바일에서 스트레스 없게 | 중 |
| 9 | 댓글·검색 부재로 티스토리 향수 | Backlog 명시 — "안 만든 것"이지 "못 만든 것"이 아님을 문서가 방어 | 하 |
| 10 | 완벽주의로 출시 지연 → 개발 열정 소진 | 90일 판정 = MVP 최소화 압력. "티스토리를 떠날 최소 조건"만으로 1차 출시 | 상 |
| 11 | 허브가 "공사 중"으로 방치 → 이력서에 못 쓰는 주소 → 존재 이유 소멸. #10의 증폭기 | 허브 v1 = 정적 한 페이지 극소화 (3.3) | 하 (단 #10 증폭) |
| 12 | 3면(허브/기술/묵상) 디자인이 제각각 어긋남 → 하나 고치면 셋 고침 → 손 놓음 | 디자인 시스템 1벌 + 사이트별 무드 변수만 오버라이드 (Phase 4에서 구조화) | 중 |

**설계 최우선순위**: #1(크롤러 폴백), #2(설교 에디터 유실 방지)는 Phase 5~7에서 최우선으로 다룬다.

## 부록. Phase 2 인터뷰 로그 요약 (3문답 + 2결정)

1. **평일 QT** → 회사 점심시간 약 20분, 데스크탑 95%. 크롤링되면 장소·기기 불문 가능. 임시저장 실사용
2. **찬양·설교 루틴** → 찬양은 평일 퇴근 후 집(데스크탑). 설교는 예배당에서 노트북으로 실시간 타이핑, 티스토리에 직접 작성·바로 발행, 다듬기 없음
3. **가사·기술 글** → 가사는 직접 타이핑 (그 자체가 묵상 — 핵심 원칙 도출). 기술 글은 주제 발생 시 AI 협업으로 작성
4. **사이트 구조** → (c) 서브도메인 분리 선택 ("c로 가면 베스트일 듯"), 루트는 (a) 프로필 허브 확정
5. **도메인** → 미구매 상태 공유. 브랜드명과 함께 Phase 4에서 결정하기로
