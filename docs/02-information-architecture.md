## 3. 작성 플로우 (Phase 3-2)

### 3.1 A-01 대시보드 — 오늘의 작성 카드

요일 기반 카드 구성:

| 요일 | 카드 1 | 카드 2 | 상시 |
|------|--------|--------|------|
| 월~토 | QT 묵상 | 찬양 묵상 | "새 기술 글" (보조 버튼) |
| 일 | 설교 묵상 | 찬양 묵상 | 〃 |

카드는 **상태를 가진 버튼**이다:

```
QT 카드 상태 (월~토)
① 초안 대기    "오늘의 QT 시작" (크롤링 완료)      → 탭 → A-04 (본문·질문 채워짐)
② 작성 중      "이어서 작성" (마지막 저장 시각)     → 탭 → A-04 (작성 내용 복원)
③ 발행 완료    "오늘 완료 ✓" (글 보기 링크)
④ 크롤러 실패  "⚠ 빈 템플릿으로 시작"              → 탭 → A-04 (빈 QT 폼) ← 수동 폴백
```

찬양·설교 카드는 동일한 상태 기계에서 ①이 "새로 시작"(크롤링 없음)인 것만 다름.

### 3.2 글 상태 모델

```
                ┌──────────────────────────────┐
                │  크롤러 (매일 아침 cron)       │
                │  QT만: DRAFT 자동 생성        │
                └──────────────┬───────────────┘
                               ▼
[없음] ──카드 탭──▶ DRAFT ◀──┐
                      │      │ 자동 저장 (debounce) + 수동 임시저장
                      │──────┘
                      │ 이탈 시 DRAFT 유지 → A-01/A-02 "이어서 작성"
                      ▼ [발행]
                  PUBLISHED ──[수정 저장]──▶ (즉시 반영)
                      │
                      ▼ [비공개 전환]
                   PRIVATE  (저작권 Open Question 대응 여지)
```

- 상태는 `DRAFT / PUBLISHED / PRIVATE` 3개로 최소화. 발행 예약 없음 (당일 작성·당일 발행 루틴)
- **발행 직후: 해당 글의 공개 페이지로 이동** (확정 — 방금 쓴 글 확인이 자연스럽고 UI 애착에 기여)

### 3.3 설교 에디터의 저장 계층 (프리모템 #2 대응)

```
키 입력 ──▶ ① 로컬 저장 (즉시, 네트워크 무관 — IndexedDB/localStorage, Phase 5 확정)
        └─▶ ② 서버 동기화 (성공 시 플래그 갱신, 실패 시 조용히 재시도)

재진입: 로컬 버전 > 서버 버전이면 복구 UI ("저장 안 된 내용이 있어요 → 복원")
```

로컬이 진실의 원천, 서버는 백업. 예배당 네트워크가 죽어도 글은 산다.

### 3.4 자동 저장 & 이어쓰기 (전 에디터 공통)

- **자동 저장(debounce) + 수동 임시저장 버튼 병행** (확정 — 네이버 블로그 패턴. 명시적으로 확정하고 싶은 순간의 안심 제공)
- 저장 상태 인디케이터("저장됨 · 방금") 상시 표시 — 신뢰의 시각화
- 이어쓰기 진입점 2곳: A-01 카드(오늘 글) + A-02 초안함(그 외)
- 발행 버튼은 에디터당 1개, **확인 모달 없이 즉시 발행** (설교 "끝나면 바로 발행" 요구. 실수는 PRIVATE 전환으로 복구 가능하므로 모달이 더 비쌈)

### 3.5 탭 카운트 — 티스토리 비교

전제: 로그인 세션 유지, `/admin` 북마크 진입.

| 루틴 | 티스토리 (현재) | 새 블로그 | 절감 |
|------|----------------|----------|------|
| QT | 진입 → 글쓰기(1) → 서식 선택(2) → 적용(3) → **본문·질문 수동 타이핑(수분)** → 답변 | 진입 → 오늘 카드(1) → **바로 답변** | depth 2 + 입력 노동 수분 → **0분** |
| 설교 | 진입 → 글쓰기(1) → 서식 선택(2) → 적용(3) → 실시간 타이핑 | 진입 → 카드(1) → 즉시 타이핑 | depth 2 + 예배 전 세팅 단축 |
| 찬양 | 진입 → 글쓰기(1) → 서식(2) → 적용(3) → URL 임베드 조작(4~) → 제목 수동 | 진입 → 카드(1) → URL 붙여넣기(2) → 제목 자동 제안 | depth 2~3 + 제목 자동화 |
| 기술 | 진입 → 글쓰기(1) → 작성 | 진입 → 새 기술 글(1) → 작성 | 동등 + 마크다운 붙여넣기 변환 |

00 문서 §4.1-① 핵심 지표("QT: 진입 → 오늘의 초안 탭 1회") 충족.

## 5. 타입별 에디터 스펙 (Phase 3-3)

> 크롤링·자동 채움 필드 공통 원칙: **잠금 없음. 불러오기만 할 뿐, 모든 필드는 수정 가능** (확정).
> 근거: 실제 QT 샘플에서 관련 구절(왕상 2:9)을 본문에 덧붙인 사용 패턴 확인 — 크롤링 이후에도 사용자가 콘텐츠를 보강한다.

### 5.1 (공통 UI) 자동 채움 영역과 작성 영역의 시각적 분리

자동 채움된 콘텐츠는 "가져온 것"임을 배경/보더로 구분하되, 클릭하면 즉시 편집 가능.

### 5.2 A-04. QT 에디터

| # | 필드 | 타입 | 필수 | 자동 채움 | 규칙 |
|---|------|------|------|----------|------|
| 1 | title | text | ✓ | ✓ 크롤러 | 편집 가능 |
| 2 | scriptureRef | text | ✓ | ✓ 크롤러 | 예: "열왕기상 2장 41~46절" |
| 3 | scriptureBody | longtext | ✓ | ✓ 크롤러 | **기본 펼침 (확정).** 편집 가능 — 관련 구절 추가 등 보강 허용 |
| 4 | annotations | 구조 배열 | — | ✓ 크롤러 | **365qt 원문의 주석 블록** (예: "그 말씀이 주의 마음에 든지라(10절) — 직역하면 …을 의미함"). 지금까지 수동 타이핑하던 대상 → 크롤링으로 제거. 편집·추가·삭제 가능 |
| 5 | questionGroups | 구조 배열 | ✓ | ✓ 크롤러 | 아래 구조 참조 |
| 6 | answers | longtext × 6 | 발행 시 권장 | — | placeholder: "질문을 묵상하고 답을 적어보세요" |
| 7 | summary | longtext | ✓ | — | 하단 고정 |

**annotations 구조:**

```
annotation = { term: text, verseRef: text(선택), body: text }
// 예: { term: "송사를 듣고 분별하는 지혜", verseRef: "11절", body: "백성을 공의와 공평으로 다스릴 수 있는 …" }
// 365qt에 주석이 없는 날도 있을 수 있음 → 빈 배열 허용, 파싱 실패 사유 아님
```

**질문 그룹 구조 (샘플 검증으로 확정):**

```
questionGroups = [
  { group: "내용관찰",    questions: [1, 2] },
  { group: "연구와 묵상", questions: [3] },
  { group: "느낀 점",     questions: [4] },
  { group: "결단과 적용", questions: [5-1, 5-2] },
]
각 question = { label, text }  // text도 편집 가능 (잠금 없음)
```

- 크롤러는 그룹 라벨까지 파싱한다 (Phase 7 크롤러 스펙에 반영할 것)
- 유효성: 발행 시 답변 6개 + summary 미완이면 **경고만, 차단 안 함** (일부만 쓰는 날도 루틴의 일부)
- 수동 폴백 모드(크롤러 실패): 1~4가 빈 입력 필드로 열림. 그룹 구조는 기본 4그룹 프리셋
- **모바일 대응 (확정)**: 작성의 95%는 데스크탑이고 모바일에서 필요한 건 **QT 답변 작성뿐**(01 §2.1). 모바일에서 고정 툴바는 **키보드 위 sticky**(`visualViewport` API로 키보드 높이 감지 → 툴바를 그 위에 고정)로 서식을 온전히 유지한다. iOS Safari 특성상 실기기 테스트 필수. 나머지 타입(설교·찬양·기술)은 데스크탑 전제라 모바일 풀대응 대상 아님

### 5.3 A-05. 설교 에디터

설계 사상: 필드 최소, 본문에 화면 전부를 양보. 방해 요소(팝업·툴바 애니메이션·자동 스크롤) 제로.

| # | 필드 | 타입 | 필수 | 자동 채움 | 규칙 |
|---|------|------|------|----------|------|
| 1 | title | text | ✓ | — | **진입 시 커서 위치 (확정).** 설교 제목 |
| 2 | scriptureRef | text | ✓(발행 시) | — | 당일 말씀 (예: "전도서 9장 7~10절") |
| 3 | scriptureBody | longtext | ✓(발행 시) | — | **말씀 본문 (샘플 검증으로 추가, 필수로 확정).** 직접 입력/붙여넣기. Backlog: "창세기 1장 2~5절" 입력 → 본문 자동 조회 — 옮겨 적기 제거라는 핵심 원칙에 부합하나, 성경 번역본(개역개정 등) 저작권·데이터 소스 검토가 선행 조건. MVP 제외 |
| 4 | body | rich longtext | ✓ | — | 라이브 속기 영역. 아래 서식 규칙 |
| 5 | summary | longtext | — | — | 예배 후 선택 작성 |

**body 서식 (샘플 검증 + 프로토타입 검증으로 확정):** 실제 설교 노트에 소제목·인용 구절·리스트가 혼재 →
순수 플레인텍스트가 아닌 **최소 서식 지원**: 소제목, 굵게, 인용(성경 구절), 리스트.
입력 방식: **정적 상단 툴바(슬림: 스타일 드롭다운/굵게/목록) + 마크다운 단축 입력(`#`, `-`, `>`) 병행.**
플로팅 툴바·팝업 등 떠다니는 UI는 금지 유지 (라이브 속기 방해 요소 제로 원칙).

- 저장: 로컬 우선 (§3.3)

### 5.4 A-06. 찬양 에디터

| # | 필드 | 타입 | 필수 | 자동 채움 | 규칙 |
|---|------|------|------|----------|------|
| 1 | youtubeUrl | url | ✓ | — | 붙여넣기 즉시 임베드 프리뷰 + oEmbed 조회 |
| 2 | title | text | ✓ | ✓ 제안 | `아티스트 - 곡명` 자동 제안 (00 문서 §7-4 휴리스틱). 실패 시 원본 제목 폴백. 항상 편집 가능 |
| 3 | sections[] | 블록 배열 | ✓ 1개 이상 | — | 아래 상세 |
| 4 | meditationAndPrayer | longtext | ✓ | — | **"묵상과 기도" (샘플 검증으로 명칭 확정).** 가사 묵상 문단 + 기도문을 자유 작성하는 단일 영역 |

**섹션 블록 구조:**

```
section = {
  label: enum(Intro/Verse/Pre-Chorus/Chorus/Bridge/Interlude/Outro) | custom(직접 입력),
  order: int,
  lyrics: longtext (선택)   // 빈 섹션 허용 — "16 Bar" 같은 연주 메모만 있는 섹션 존재 (샘플 검증)
}
```

- 라벨 7종 + **직접 입력 옵션 (확정)** — Tag, Refrain 등 예외 대응
- Verse 자동 넘버링 (동일 label 순서 기준)
- **섹션 반복은 각각 독립 블록** (샘플: Verse·Chorus가 2회 이상 등장. 복제 버튼으로 반복 입력 지원 검토 — Phase 5)

**인터랙션 (타이핑 흐름 보호):**

| 동작 | 방법 |
|------|------|
| 추가 | 블록 끝 `Enter 2회` 또는 "+ 섹션". 라벨 선택은 키보드로 완결 (방향키/단축키) |
| 정렬 | 드래그 핸들 + 키보드 `Alt+↑↓` 병행 |
| 삭제 | 빈 블록 Backspace 또는 블록 메뉴 |
| 라벨 변경 | 라벨 클릭 → 인라인 드롭다운 (블록 재생성 없음, 가사 유지) |
| 새 블록 기본 라벨 | 마지막 사용 라벨 + 넘버링. 고도화(다음 섹션 추론)는 실사용 후 판단 |

- 세부 인터랙션은 구현 후 실사용 검증 전제 (본인 확인: "구현해봐야 좀 알듯")
